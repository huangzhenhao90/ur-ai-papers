# arXiv 增量入库可靠性与 30 天回补设计

## 背景与根因

论文 `arXiv:2608.04205`（MatrAIx）能够被当前 arXiv 查询命中，也能通过 `persona` 和 `user evaluation` 等强信号过滤，却没有进入线上论文库。

根因是原始记录去重时的事务边界错误：抓取循环在遇到唯一键冲突后调用整个 SQLAlchemy Session 的 `rollback()`。这会撤销同一批次中此前已成功 `flush()`、但尚未提交的新记录。计数器没有随事务回滚，因此任务仍被标记为成功，形成“报告抓到、数据库未保存”的静默数据丢失。

线上数据库快照证明了这一点：2026-08-10 的 `cs.AI` 增量运行报告抓取 136 条，但该运行实际关联的 `raw_records` 为 0 条。相同现象也存在于其他 arXiv 分类。每日英文期刊增量和历史导入入口采用了同类回滚写法，也存在相同风险。

## 目标

- 重复记录只影响自身，不得回滚同批次中的其他新记录。
- arXiv、英文期刊增量和历史导入入口使用同一套安全入库机制。
- 日志能够区分 API 返回、成功新增和重复跳过，避免静默丢失。
- 增加合成用户研究相关召回信号，覆盖与 MatrAIx 类似的论文表述。
- 修复后仅回补最近 30 天，不进行 2023 年以来的全量回补。
- 将 MatrAIx 固化为回归样本，并验证其进入数据库和前端导出。

## 非目标

- 不修改 SQLite 数据库表结构。
- 不取消 arXiv 的关键词预过滤或后置 LLM 双打分。
- 不扩大到 30 天以前的历史数据修复。
- 不改变前端的论文展示门槛。

## 方案选择

### 采用：逐条数据库保存点

新增一个共享的原始记录写入函数。每条记录在 `session.begin_nested()` 建立的保存点内执行 `flush()`；若触发唯一键冲突，只回滚该保存点并返回“重复”，外层事务及此前新增记录保持有效。

选择保存点的原因：

- 保留数据库唯一约束作为最终一致性保障。
- 不依赖预加载 ID 集合，避免并发竞态。
- 不依赖 SQLite 专属的 `INSERT OR IGNORE`，继续使用现有 SQLAlchemy 模型。
- 单次分类通常只有数百条候选，逐条保存点的性能成本可接受。

### 未采用：预加载已有 ID

预加载集合能减少异常开销，但查询后仍可能发生并发写入，最终仍需处理唯一键冲突。它可以作为未来性能优化，但不作为可靠性边界。

### 未采用：SQLite `INSERT OR IGNORE`

该方案简洁高效，但会把入库逻辑绑定到 SQLite 方言，并绕开当前 ORM 写入模式。当前数据规模不足以抵消这项维护成本。

## 架构与组件

### 1. 安全原始记录写入器

在 pipeline 层新增单一职责模块，输入为 Session、运行 ID、来源、来源记录 ID 和 payload，输出为是否新增成功。

行为约定：

- 新记录：保存并返回 `True`。
- 唯一键重复：仅回滚当前保存点并返回 `False`。
- 其他数据库错误：携带来源和记录 ID 上下文向上抛出，由来源级任务标记失败。

### 2. 抓取入口统一接入

以下入口改用共享写入器：

- 每日英文期刊增量。
- 每日 arXiv 增量。
- arXiv 历史抓取入口。
- 英文期刊 OpenAlex/Crossref 历史抓取入口。

每个来源运行维护三个计数：

- `seen`：API 返回且具备来源 ID 的候选数。
- `inserted`：本次实际新增数。
- `duplicate`：被唯一约束跳过的重复数。

现有 `SourceRun.records_fetched` 保持原字段，不做数据库迁移；写入本次实际新增数，并在控制台完整打印三项统计。

### 3. 持久化一致性检查

来源级任务提交后，查询该 `run_id` 实际关联的 `raw_records` 数量，并与 `inserted` 比较。两者不一致时任务失败，不得继续以 `success` 状态完成。

这一检查负责发现未来可能出现的其他事务边界错误。

### 4. 合成用户研究召回信号

在 arXiv 候选查询和强信号过滤中补充一组窄范围词组：

- `simulated user` / `simulated users`
- `synthetic user` / `synthetic users`
- `user simulation` / `user simulator`
- `persona agent` / `persona agents`
- `virtual user` / `virtual users`

这些词只负责让候选进入后置 LLM 双打分，不直接决定前端收录。避免加入过宽的 `human evaluation`，因为该词在纯模型评测论文中误报率较高。

## 数据流

1. Connector 按分类和召回词获取最近 30 天候选。
2. 每条候选通过安全写入器进入独立保存点。
3. 重复记录被局部跳过；新记录保留在外层来源事务中。
4. 来源完成后提交外层事务，并执行持久化数量核验。
5. 新增 raw record 进入 normalize；强信号过滤不通过的记录仍留在 raw 层供审计。
6. 通过过滤的论文进入 LLM 双打分、摘要和标题翻译。
7. 符合现有前端阈值的论文进入 JSON 和 RSS 导出。

## 错误处理

- 唯一键冲突是正常重复，不降低来源运行状态。
- 网络或解析异常沿用来源级失败处理，并记录上下文。
- 非唯一键数据库异常不得被当作重复吞掉。
- 持久化数量不一致视为可靠性故障，任务失败并阻止错误成功状态。
- 30 天回补继续使用现有 LLM 每日上限和安全阀，避免意外费用扩张。

## 测试与验收

### 单元测试

- 新记录能够保存。
- 重复记录返回跳过，且不会删除同一事务中此前保存的新记录。
- “新记录 → 重复记录 → 新记录”序列最终持久化两条新记录。
- 非唯一键数据库错误不会被吞掉。
- MatrAIx 标题和摘要能够通过强信号过滤。
- 新增的合成用户关键词出现在 arXiv 查询候选词中。

测试使用临时 SQLite 数据库和 Python 标准库 `unittest`，不增加运行时依赖。

### 集成验收

- 使用 `LOOKBACK_DAYS=30` 执行抓取、归一化和导出流程。
- `raw_records` 中存在 `2608.04205`。
- `papers` 中存在对应论文，且 `is_arxiv=True`。
- 来源运行日志中的新增数与实际 `run_id` 持久化数量一致。
- 导出数据包含 MatrAIx；若 LLM 分数未达到现有门槛，应在数据库中保留并能解释未展示原因。
- 现有本地未提交的 `web/public/data/meta.json` 变更不被覆盖或提交。

## 发布与回补

代码和测试通过后，将增量窗口临时设置为 30 天运行一次。之后恢复默认 14 天日常窗口。回补只处理最近 30 天；更早数据保持不变。

实施应基于最新 `origin/main`，同步时必须保留当前工作区已有的 `web/public/data/meta.json` 未提交变更。设计文档、代码修复和自动生成的数据应分开提交，避免混入用户已有改动。
